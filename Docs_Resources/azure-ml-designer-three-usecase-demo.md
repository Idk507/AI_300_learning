# Azure Machine Learning Designer: Three End-to-End Drag-and-Drop Demos (ML, Computer Vision, NLP)

## How to Use This Document

This is a hands-on, click-by-click operational runbook, written the way a data scientist would actually execute it inside Azure Machine Learning studio's Designer canvas, using classic prebuilt (v1) components and the built-in sample datasets. It covers three complete use cases end to end: a tabular regression use case for core machine learning, an image classification use case for computer vision, and a text classification use case for natural language processing. For every use case you get the exact sequence of what to drag, what to connect, what to configure in the settings pane, how to submit and validate the run, how to convert the trained pipeline into an inference pipeline, how to deploy that inference pipeline as a live real-time endpoint or as a published batch endpoint, and how to test the result. A single governance note applies to all three demos and should be read before you start.

> **Platform lifecycle notice.** These walkthroughs use Designer's classic prebuilt (v1) components, which is the exact toolset used in the screenshot you shared earlier in this conversation. Microsoft's own documentation states that SDK v1, which classic Designer pipelines depend on, is deprecated as of March 31, 2025, with support ending June 30, 2026, a date that has already passed relative to today. Existing v1 workflows will continue to run, but they no longer receive updates and carry unmitigated security and breaking-change exposure. Treat everything below as an excellent way to learn the orchestration concepts and to demo capability quickly, but for any workload you intend to keep running in production, replan it using custom v2 components on SDK v2 or CLI v2, exactly as recommended in the earlier part of this conversation.

## Shared Prerequisites for All Three Demos

Before starting any of the three pipelines, you need one Azure Machine Learning workspace, reachable at `https://ml.azure.com`, and at least one compute cluster. In the studio, open **Compute** from the left sidebar, select **Compute clusters**, then **+ New**, and provision a CPU-based cluster (a `Standard_DS3_v2` sized node with minimum nodes set to 0 is sufficient and cost-efficient for the ML and NLP demos, since it autoscales down to zero and stops billing when idle) for the tabular and text demos, and a GPU-based cluster (a `Standard_NC6`-class SKU) for the computer vision demo, since DenseNet and ResNet training is GPU-accelerated deep learning. Every pipeline you build below is created the same way: from the studio home page, select **Designer** in the left sidebar, then under **Classic prebuilt**, select **Create a new pipeline using classic prebuilt components**. Immediately rename the pipeline draft using the pencil icon next to the auto-generated name, since giving each draft a meaningful name (for example, "Automobile price prediction," "Animal image classification," "SP500 text classification") keeps your workspace organized as you accumulate runs.

## Demo 1 — Machine Learning: Automobile Price Regression

### Objective and Dataset

You will train a linear regression model that predicts the price of a car from its technical specifications, using the built-in **Automobile price data (Raw)** sample dataset, which contains 205 rows and 26 columns describing individual automobiles. This is the canonical first pipeline for learning Designer because it exercises every stage of a classic ML workflow: import, clean, split, train, score, and evaluate.

### Step-by-step pipeline construction

**Step 1: Import the sample data.** In the component palette on the left of the canvas, select the **Component** tab, then expand **Sample data**. Locate **Automobile price data (Raw)** in the list and drag it onto the canvas. Right-click the node and select **Preview Data** to inspect the 205 rows and 26 columns; click through a few columns to see their distributions and note that several columns, particularly `normalized-losses`, have visibly missing values.

**Step 2: Remove the problematic column.** Search the component palette for **Select Columns in Dataset** and drag it onto the canvas below the dataset node. Connect the dataset's output port (the small circle at the bottom of the node) to the input port (the small circle at the top) of Select Columns in Dataset. Select the component, open its details pane (the arrow icon under Pipeline interface, or simply double-click the node), and select **Edit column**. In the column selector, expand the **Include** dropdown and choose **All columns**, then click the **+** to add a new rule, set that rule to **Exclude** by **Column names**, and type `normalized-losses` into the text box. Select **Save**. Optionally expand **Node information** in the details pane and add the comment "Exclude normalized losses" so the graph is self-documenting.

**Step 3: Clean the remaining missing values.** Search for **Clean Missing Data**, drag it onto the canvas, and connect it to the output of Select Columns in Dataset. Open its details pane, select **Edit column**, set **Include** to **All columns**, and save. In the **Cleaning mode** dropdown, select **Remove entire row**. This ensures no row entering the training step still contains a null value, since classic trainers silently skip such rows and you want that skipping to be explicit and auditable rather than implicit.

**Step 4: Split the data into training and test sets.** Search for **Split Data**, drag it onto the canvas, and connect the **left** output port of Clean Missing Data (the cleaned data) to its input. This distinction matters: the left port carries the cleaned rows, while the right port carries the discarded rows, and connecting the wrong one silently corrupts your training set. Open the Split Data details pane and set **Fraction of rows in the first output dataset** to `0.7`, which reserves 70 percent for training (available on the left output port) and 30 percent for testing (right output port).

**Step 5: Define and attach the algorithm.** Search for **Linear Regression** and drag it onto the canvas; this node only configures the algorithm and is never executed by itself. Search for **Train Model** and drag it onto the canvas. Connect the output of Linear Regression to the **left** input port of Train Model, and connect the **left** (training) output port of Split Data to the **right** input port of Train Model. Open the Train Model details pane, select **Edit column**, set the mode to **Column names**, and type `price` exactly, matching the case of the source column, into the text box, which tells the trainer which column is the regression target.

**Step 6: Score the held-out test set.** Search for **Score Model**, drag it onto the canvas, connect the output of Train Model to its left input port, and connect the **right** (test) output port of Split Data to its right input port.

**Step 7: Evaluate the model.** Search for **Evaluate Model**, drag it onto the canvas, and connect the output of Score Model to its left input. Your finished graph should read top to bottom: Automobile price data (Raw) into Select Columns in Dataset into Clean Missing Data, which fans out into Split Data, which feeds both Train Model (via Linear Regression) and Score Model, which feeds Evaluate Model.

### Submitting and validating the run

Select **Configure & Submit** at the top right of the canvas. In the **Basics** step of the wizard, name the experiment and job. In **Inputs & Outputs**, leave this empty since no input or output was promoted to pipeline level. In **Runtime settings**, select the CPU compute cluster you provisioned earlier as the default compute for every component. Review the settings and select **Submit**. The first run can take up to 20 minutes because the cluster must allocate a node from zero; subsequent runs reuse the allocated node and Designer's step-level output caching, so they complete much faster. Once the job finishes, right-click **Score Model** and select **Preview data > Scored dataset** to visually compare predicted versus actual prices, and right-click **Evaluate Model** and select **Preview data > Evaluation results** to review Mean Absolute Error, Root Mean Squared Error, Relative Absolute Error, Relative Squared Error, and the Coefficient of Determination (R-squared), where lower error values and an R-squared closer to 1.0 both indicate a better fit.

### Implementing inference

**Real-time inference (interactive, request-response scoring).** From the **Jobs** page, open the completed pipeline job, select the ellipsis (**...**) above the canvas, and choose **Create inference pipeline > Real-time inference pipeline**. Designer automatically performs several transformations for you: it freezes the trained model as a registered Dataset component, strips out training-only nodes such as Train Model and Split Data, re-inserts the frozen trained model, and adds **Web Service Input** and **Web Service Output** components marking where live request data enters and where the response leaves. Because Web Service Input by default inherits the schema of whatever it is wired in parallel with, and in this case that is the raw dataset which still includes the `price` target column, add a **Select Columns in Dataset** component immediately after Web Service Input to drop the `price` column, since a real caller will never know the price in advance, and wire its output into the same downstream port that Web Service Input used to feed. Select **Configure & Submit**, run this inference pipeline once using the same compute and experiment as before, then open the job detail page and select **Deploy**. If you don't yet have an inferencing cluster, go to **Compute > Kubernetes Clusters > + New > AksCompute**, choose a nearby region, name it (for example `aks-compute`), and select **Create**; provisioning takes roughly 15 minutes. Back on the deploy dialog, select the AKS cluster, review the advanced settings (Application Insights diagnostics, scoring timeout of 60000 ms by default, autoscaling with a default of 1 to 10 replicas targeting 70 percent utilization, and CPU/memory reservation), and select **Deploy**. Once deployment succeeds, go to **Endpoints**, open the deployed endpoint, and use the **Test** tab to submit sample technical specifications and confirm a plausible predicted price comes back; the **Consume** tab gives you the REST URI, authentication keys, and sample client code for wiring the endpoint into an external application; the **Deployment logs** tab helps you debug container startup issues.

**Batch inference (scheduled or bulk scoring).** As an alternative or complement to the real-time endpoint, you can create a batch inference pipeline the same way, choosing **Create inference pipeline > Batch inference pipeline** instead, then select **Publish** on that pipeline to register it under a **pipeline endpoint**. Publishing assigns the pipeline a version under a named endpoint, exposes a REST trigger URL callable from any external system including non-Python clients such as Azure Data Factory, Azure DevOps, or GitHub Actions, and lets you designate a default version while retaining older versions for rollback. This pattern is the correct choice whenever you need to score a large batch of new cars overnight rather than answer individual, latency-sensitive requests.

## Demo 2 — Computer Vision: Image Classification with DenseNet

### Objective and Dataset

You will build an image classification model using transfer learning on the pretrained DenseNet convolutional architecture, following the pattern of Designer's built-in **Image Classification using DenseNet** sample template, which by default uses an Animal Image Dataset. The same graph shape works with any labeled image collection you substitute in.

### Step-by-step pipeline construction

**Step 1: Start from the template or build manually.** The fastest path is, on the Designer homepage, to open the built-in sample pipeline named **Image Classification using DenseNet** (found under the computer vision samples section), which arrives pre-wired; you can then simply swap the input dataset for your own images. To build it from scratch instead, drag your labeled image dataset onto the canvas (or, for a custom dataset, register your images in the workspace's Datasets section first).

**Step 2: Convert to the image directory format.** Search the palette for **Convert to Image Directory** and connect your image dataset to it. Classic vision components do not accept datasets produced by the studio's Data Labeling tool; they require the directory structure that this component produces, so this step is mandatory regardless of where your source images came from.

**Step 3: Split into training and validation sets.** Search for **Split Image Directory**, connect it to the output of Convert to Image Directory, and configure the split fraction (a 70/30 or 80/20 split is typical) to produce a training subset and a validation subset.

**Step 4: Define the DenseNet algorithm.** Search for **DenseNet**, drag it onto the canvas, and in its details pane set **Model name** to one of the supported structures, `densenet121`, `densenet161`, `densenet169`, or `densenet201`; `densenet121` is the standard starting point because it balances accuracy and training cost well for a first demo.

**Step 5: Train with Train PyTorch Model.** Search for **Train PyTorch Model**, drag it onto the canvas, connect the DenseNet component's output to its algorithm input, and connect the training-split output of Split Image Directory to its data input. Open its details pane and set the number of training epochs (a small number such as 5 to 10 is enough for a demo; production accuracy typically needs more) and confirm the compute target assigned to this node is your GPU cluster, since deep CNN training is computationally intensive and will run unacceptably slowly on CPU-only compute.

**Step 6: Score against the validation split.** Search for **Score Image Model**, drag it onto the canvas, connect the trained model output of Train PyTorch Model to it, and connect the validation-split output of Split Image Directory to its data input.

**Step 7: Evaluate.** Search for **Evaluate Model**, connect the output of Score Image Model to it, exactly as in the tabular demo, to compute classification accuracy, precision, recall, and a confusion matrix over the held-out validation images.

### Submitting and validating the run

Select **Configure & Submit**, choose your GPU compute cluster in **Runtime settings**, and submit. Because DenseNet training is materially heavier than tabular regression, expect wall-clock durations of many minutes to a few hours depending on dataset size, epoch count, and node availability; monitor progress on the job detail page's real-time log stream. Once complete, right-click **Evaluate Model** and preview the evaluation results to review classification accuracy and inspect misclassified examples through the Score Image Model output preview, which shows each image alongside its predicted and actual label.

### Implementing inference

**Real-time inference.** Exactly as in Demo 1, open the completed job, select **Create inference pipeline > Real-time inference pipeline**. Designer freezes the trained DenseNet model, strips out Train PyTorch Model and Split Image Directory, and inserts Web Service Input and Web Service Output around a slimmed graph that runs Convert to Image Directory followed by Score Image Model against whatever image the caller submits. Submit this inference pipeline once to validate it, then select **Deploy** from the job detail page, choose or create an AKS inferencing cluster (for image workloads, prefer a GPU-backed AKS node pool if your expected request volume and latency requirements justify the cost, otherwise a CPU node pool is acceptable for low-traffic demos since inference is cheaper than training), configure autoscaling and Application Insights as in Demo 1, and select **Deploy**. Test the resulting endpoint from the **Test** tab by uploading a new image and confirming the returned predicted class and confidence score are sensible; use the **Consume** tab to retrieve the endpoint's scoring URI and key for integration into a mobile app, web app, or IoT edge scenario that needs live image classification.

**Batch inference.** For scoring large image archives, such as classifying an entire folder of newly captured images overnight, build a batch inference pipeline the same way (**Create inference pipeline > Batch inference pipeline**), point its input at a folder datastore reference instead of Web Service Input, and **Publish** it to a pipeline endpoint exactly as described in Demo 1, giving you a REST-triggerable, versioned batch scoring job orchestrable from Azure Data Factory or a scheduled trigger.

## Demo 3 — Natural Language Processing: Text Classification on the Wikipedia SP 500 Dataset

### Objective and Dataset

You will train a multiclass classifier that predicts a company's business category from free text, using the built-in **Wikipedia SP 500** sample dataset, which is derived from the Wikipedia article text of S&P 500 companies. This demo mirrors Designer's built-in **Text Classification – Wikipedia SP 500 Dataset** sample and demonstrates the standard NLP featurization pattern: clean text, convert it into numeric features, then hand those features to a conventional classifier.

### Step-by-step pipeline construction

**Step 1: Import the sample data.** In the component palette, select **Component > Sample data**, locate **Wikipedia SP 500 Dataset**, and drag it onto the canvas. Right-click and **Preview Data** to confirm it contains a free-text article column alongside a company category label column; note that the row count is slightly under 500 since articles could not be located for every company.

**Step 2: Preprocess the text.** Search for **Preprocess Text**, drag it onto the canvas, connect it to the dataset, and in its details pane select the text column to process, then enable the standard cleaning options: lowercasing, stop word removal, punctuation and special character removal, and optionally stemming or lemmatization, all of which reduce vocabulary noise before featurization.

**Step 3: Extract numeric text features.** Search for **Extract N-Gram Features from Text**, drag it onto the canvas, and connect the cleaned text output to it. In its details pane, select the preprocessed text column as the input, set **Vocabulary mode** to **Create**, choose **TF-IDF** as the weighting function (term-frequency inverse-document-frequency, which down-weights very common, low-information words while up-weighting rare, distinctive ones), and set the n-gram length, typically 1 or 2, controlling whether the model looks at single words (unigrams) or word pairs (bigrams) as features. This converts the variable-length article text into a fixed-width numeric feature vector per company, one column per n-gram term in the learned vocabulary.

**Step 4: Drop the now-redundant raw text column.** Search for **Select Columns in Dataset**, connect it after the N-Gram extraction step, and configure it to exclude the original free-text column, retaining only the numeric TF-IDF feature columns plus the label column, since leaving the raw text in place adds no value to a numeric classifier and only bloats the dataset.

**Step 5: Split the data.** Search for **Split Data**, connect it to the output of Select Columns in Dataset, and set the split fraction to `0.7`, exactly as in Demo 1, giving you a training subset (left port) and a test subset (right port).

**Step 6: Define and attach the classifier.** Because the feature space produced by n-gram extraction is large and sparse, drag **Multiclass Logistic Regression** onto the canvas, which is well suited to high-dimensional sparse inputs. Drag **Train Model** onto the canvas, connect Multiclass Logistic Regression to its left (algorithm) input, connect the training-split (left) output of Split Data to its right (data) input, open its details pane, select **Edit column**, and set the label column to the company category column name.

**Step 7: Score and evaluate.** Drag **Score Model** onto the canvas, connect Train Model's output to its left input and the test-split (right) output of Split Data to its right input. Drag **Evaluate Model** onto the canvas and connect Score Model's output to it, which will report accuracy, macro and micro averaged precision and recall, and a per-class confusion matrix appropriate to a multiclass problem.

### Submitting and validating the run

Select **Configure & Submit**, select your CPU compute cluster in **Runtime settings** (text classification on a dataset of this size does not require GPU compute), and submit. Once complete, right-click Score Model to preview predicted versus actual company categories, and right-click Evaluate Model to review the classification metrics; because this is a multiclass problem with class imbalance likely present across company categories, pay particular attention to the per-class recall in the confusion matrix rather than overall accuracy alone, since overall accuracy can look artificially strong if a few large categories dominate the dataset.

### Implementing inference

**Real-time inference.** From the completed job, select **Create inference pipeline > Real-time inference pipeline**. Designer freezes the trained Multiclass Logistic Regression model, removes Train Model and Split Data, and wires in Web Service Input and Web Service Output around a slimmed graph of Preprocess Text into Extract N-Gram Features from Text (now operating in **Read vocabulary** mode against the vocabulary learned during training, rather than **Create** mode, which is critical: reusing the training-time vocabulary, rather than recomputing a new one from whatever text a caller submits, is what prevents train-serve skew) into Select Columns in Dataset into Score Model. Submit this inference pipeline once to validate it, then select **Deploy**, choose or create your AKS inferencing cluster, configure the same advanced deployment settings covered in Demo 1, and deploy. Test the endpoint from the **Test** tab by submitting a new snippet of company description text and confirming a sensible predicted category and confidence score are returned; retrieve the REST URI and key from the **Consume** tab for integrating live text classification into a support ticket router, a document tagging pipeline, or a chatbot skill.

**Batch inference.** For classifying a large archive of documents at once, follow the same **Create inference pipeline > Batch inference pipeline** and **Publish** pattern described in Demo 1 and Demo 2, giving you a REST-triggerable, versioned pipeline endpoint suitable for nightly bulk document classification jobs.

## Common Publishing, Versioning, and Update Pattern (Applies to All Three Demos)

Every one of the three demos converges on the same production operating model once the underlying trained model needs to be refreshed. When you retrain the underlying training pipeline, whether because new automobile data, new labeled images, or a refreshed text corpus arrived, follow the same update sequence in every case: open your existing training pipeline draft from the Designer homepage (or clone the previous training job into a new draft), modify and resubmit it, and once the new job completes, right-click the relevant training node (Train Model, Train PyTorch Model, or the equivalent) and select **Register data**, giving the newly trained model a name and registering it as a File-type dataset. Open your inference pipeline draft (or clone the previous inference job into a new draft) and manually replace the old trained-model node, shown in the canvas as an `MD-xxxx` node, with the newly registered dataset; if any upstream transformation logic also changed, register that transformation's output the same way and swap the corresponding `TD-xxxx` node. Resubmit the modified inference pipeline, and once it completes, deploy it either to your existing real-time endpoint, which performs a rolling update of the live service with zero manual endpoint recreation, or publish it as a new version under your existing batch pipeline endpoint, optionally promoting it to be the new default version while retaining the previous version for rollback safety. Be aware of a few platform limitations that apply uniformly across all three demos: **Import Data** and **Export Data** components are automatically removed if present in a graph deployed to a real-time endpoint, since real-time scoring cannot reach out to arbitrary external datastores mid-request; datasets referenced inside a real-time inference graph currently must originate from a Blob datastore, and if yours does not, route it through a **Select Columns** component set to select all columns, register that component's output as a new File dataset, and substitute that registered dataset in place of the original; and any **Enter Data Manually** component not wired to the same port as Web Service Input will silently not execute during a live HTTP call, so if you need constant reference data at inference time, register it as a dataset rather than leaving it as an Enter Data Manually node.

## Summary, Recommendations, and Trade-offs

All three demos above follow one identical architectural skeleton regardless of domain: ingest data through a Data Input/Output or Sample Data node, clean and shape it through Data Transformation or domain-specific preprocessing components, hand a prepared, numeric, split dataset to a Train Model-style wrapper paired with an algorithm-definition component, score and evaluate the result, and only then convert the validated training pipeline into a slimmed inference pipeline that either serves live requests behind a real-time AKS-backed endpoint or runs on a schedule behind a published, versioned batch pipeline endpoint. Choose the real-time path when individual predictions are needed synchronously and at low latency, such as quoting a car price to a website visitor, classifying a single uploaded photo, or routing one support ticket, and accept the standing cost of a running AKS cluster and the operational overhead of endpoint monitoring in exchange for that responsiveness. Choose the batch path when you are scoring large volumes on a predictable cadence, such as nightly re-scoring an entire vehicle inventory, classifying a day's worth of newly ingested images, or bulk-tagging a document archive, and benefit from lower cost since compute only runs during the scheduled window, plus simpler integration with orchestrators such as Azure Data Factory that already speak REST. Across all three demos, the recurring engineering discipline worth internalizing, independent of Designer specifically, is the strict separation between the artifact-producing training graph and the artifact-consuming inference graph, the explicit registration and versioning of every trained model and learned transformation (vocabulary, encoder, or scaler) rather than leaving it implicit inside a script, and the enforcement of Web Service Input and Web Service Output as the only sanctioned request/response boundary, all of which are exactly the properties a mature MLOps pipeline needs, and are precisely what you should carry forward, this time expressed as versioned YAML component specifications and SDK v2 pipeline jobs rather than classic canvas nodes, once you move any of these three demos from prototype into durable production.
